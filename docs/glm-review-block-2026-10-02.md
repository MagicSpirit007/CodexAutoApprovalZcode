# GLM 自动审查请求被拦截：2026-10-02 排查

## 结论

本次失败发生在 GLM 供应商请求阶段，自动审批尚未得到 allow / deny 结论。
原生日志记录 `request has been blocked due to unusual activity.`，并将该请求标记为不可重试。
自动审批因技术失败转为人工确认，不能据此判断待执行的 Chrome 截图命令属于危险操作。

同一会话、同一轮次、同一供应商与模型的主请求成功，紧接着的自动审查请求失败。
现有证据不足以判定供应商内部的具体拦截规则，也不能把某一个请求头、提示词、账号状态或网络地址认定为根因。

## 为什么 0.1.3 仍会出现

[0.1.3 验收记录](desktop-acceptance.md) 已记录：增加独立审查模型后，真实 DeepSeek 审查成功，但 GLM 的隔离验收在原生凭据准备阶段停止，未发出 GLM 模型请求。因此那次验收没有证明 GLM 原拦截解除。

独立审查模型属于可选配置；旧配置默认跟随会话，不会自动换供应商。本次用户仍使用 GLM 审查，因此可以继续遇到此前未解除的供应商拦截。

## 修复范围

由根代理设计错误边界与验收约束，GPT-6.1-Sol 子代理负责具体实现。规格见宿主 `docs/specs/codex-auto-approval.md` 的 “Explicit provider interception diagnostics” 章节。

- 在现有宿主错误归一化边界，把明确的 unusual-activity 阻断识别为 `provider_request_blocked`，不可重试。
- 保留原生适配器已记录的脱敏状态码和请求编号；只读取明确允许的诊断字段。
- 通过已有人工确认窗口说明供应商拦截及处理路径，保留原始脱敏诊断。
- 普通 405 不等于异常活动拦截；认证、临时网络失败及其他既有行为继续按各自分类处理。
- 继续转人工，不执行被等待的动作，不将技术失败算作策略拒绝，不自动更换模型或请求身份。

此改动修复错误分类、诊断信息丢失和提示不清的问题；不代表供应商已解除拦截。既有发行 ZIP、正在运行的桌面和用户配置均保留。

## 当前处理方式

可以使用当前人工审批处理这一次动作。需要指定独立审查模型时，使用已有入口：**设置 → 插件 → CodexAutoApproval → 高级信息 → 审查模型**，选择后保存。供应商、地址、协议和凭据仍由原生模型管理界面负责。

若继续使用当前 GLM 通道，需由供应商确认本次阻断原因；本地改动不能保证其恢复。不要将更改提示、增加重试或伪装请求归属视为已验证的修复。
